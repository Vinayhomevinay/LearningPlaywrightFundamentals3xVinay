The request path

1

Client Code. Your test calls Playwright's API — page.click(), page.goto(), expect() — from whichever language binding you installed.

2

WebSocket connection. One persistent, bidirectional socket links the client library to the server. Commands and events flow both ways over it — nothing is polled.

3

JSON-RPC format. Every call and every response is a plain JSON object with a method, its params, and an id. That's how a Python script can drive a Node.js process without sharing a runtime.

4

Playwright Server (BrowserServer). The real driver, written in Node.js. It receives JSON-RPC calls from any client language, launches and manages browser processes, and translates commands into engine-specific instructions.

5

CDP / CDP+. The server talks to each rendering engine over the Chrome DevTools Protocol — natively for Chromium, and over Playwright's own CDP-style protocol for its patched Firefox and WebKit builds.

Rendering engines

6

Chromium. Speaks real CDP directly, so this same path also works against stock Chrome and Edge.

7

Firefox. A build patched by the Playwright team so it exposes a CDP-like protocol Firefox doesn't natively support.

8

WebKit. Same idea as Firefox — a patched build giving Safari's engine the same protocol surface.

Inside a browser

9

Browser. One OS-level process per engine, started and owned by the server.

10

BrowserContext. An isolated, incognito-style session — its own cookies, storage, and cache. Tests are typically given a fresh context each run for isolation.

11

Page. One tab inside a context. A single context can hold several pages at once, e.g. a page that opens a pop-up.

Note on terminology: * means the label is simplified for this architecture diagram. CDP is used for Chromium, while CDP+ is used for Firefox and WebKit to represent Playwright's browser-specific CDP-like communication layer. The CDP+ label here is a diagram convention, not the name of an official protocol.
